Question 01
What is DocuChat AI, why was it built, and how does it work at a high level?
Level 1 Project Overview
📌 WHAT IS THIS? (Definition & Concept)
DocuChat AI is a 100% local, privacy-preserving, enterprise-grade Retrieval-Augmented Generation (RAG) platform. It allows users to upload complex documents (PDFs, DOCX, TXT, Excel) and chat with them without hallucinations, featuring automated single-line visual PDF highlighting and an integrated dual-mode chat workstation.
🎯 WHY WE USE IT? (Need & Value)
Standard generative AI tools either suffer from hallucinations, leak proprietary enterprise data to external cloud APIs, or force users to manually skim through 50-page documents to verify claims. DocuChat AI guarantees deterministic provenance, zero cloud API costs, complete on-premises privacy, and visual proof for every assertion.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
The system follows a 3-tier reactive pipeline: (1) Ingestion: PyMuPDF/Docling extracts text, tables, and bounding box coordinates into ~400-token chunks. (2) Storage: Dense embeddings (FastEmbed BGE-small) are indexed in Qdrant Vector DB, while sparse tokens are indexed in BM25Plus JSON files. (3) Hybrid Retrieval & Grounded Generation: User queries are expanded via Multi-Query rewriting, searched across dense and sparse indices in parallel, merged with Reciprocal Rank Fusion (RRF), reranked via Max-Scaling, and passed to a local Qwen 2.5 7B LLM streaming via Server-Sent Events (SSE). Bounding box scoring highlights the exact answer line on the PDF canvas.
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE
In an interview, start with the 3 pillars: 100% Local Privacy, Hybrid Dense+Sparse Search, and Single-Sentence Visual PDF Highlighting. Explain that it solves both the provenance problem and the cloud dependency problem.
Question 02
What is Retrieval-Augmented Generation (RAG), and why is it preferred over fine-tuning or prompt-only LLMs?
Level 1 RAG Fundamentals
📌 WHAT IS THIS? (Definition & Concept)
RAG is an AI architectural pattern that dynamically retrieves relevant factual documents from an external knowledge store (vector/lexical database) and injects them into an LLM prompt as context before generating a response.
🎯 WHY WE USE IT? (Need & Value)
Fine-tuning updates model weights, which is computationally expensive, suffers from catastrophic forgetting, cannot be easily updated with real-time private documents, and still hallucinates plausible facts. RAG decouples knowledge storage from reasoning: knowledge is updated instantly upon document upload, access control is trivial, and every answer can be cited with exact page coordinates.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
Instead of expecting the LLM to memorize facts, DocuChat uses the LLM purely as a reasoning engine over the retrieved context. When a user asks a question, only the relevant 3-5 chunks (~1,500 tokens) are injected into the SystemMessage with strict instructions to answer only from provided context, or state 'I do not have enough information.'
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE
Emphasize: 'Fine-tuning is for teaching the model how to speak (style/syntax/tone); RAG is for giving the model what to say (facts/live data/provenance).'
Question 03
What is the difference between Naive RAG and Production Advanced RAG? Where does DocuChat AI fit?
Level 1 Architecture
📌 WHAT IS THIS? (Definition & Concept)
Naive RAG consists of a simple linear pipeline: naive character chunking → vector embedding → cosine top-k search → prompt concatenation → raw completion. Advanced Production RAG includes multi-stage pre-retrieval (query rewriting), hybrid retrieval (dense + sparse), post-retrieval (fusion & reranking), and visual grounding.
🎯 WHY WE USE IT? (Need & Value)
Naive RAG fails catastrophically in production due to low recall on exact terms (serial numbers, names, IDs), dropped secondary chunks, context fragmentation, and unverified hallucinations with no visual feedback.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
DocuChat AI is an Advanced Modular RAG platform: (1) Pre-Retrieval: Multi-Query sub-expansion resolving pronouns; (2) Retrieval: Parallel FastEmbed dense vector + BM25Plus sparse lexical; (3) Post-Retrieval: Reciprocal Rank Fusion (k=60) + Max-Scaled reranking; (4) Visual Grounding: Bounding box scoring mapping the exact winning sentence to PDF.js canvas.
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE
Mention how Naive RAG fails on keyword lookups (e.g., product code 'SKU-9921'), and how DocuChat overcomes this using BM25Plus sparse fusion alongside dense vectors.

Question 06
What is the role of FastAPI and Uvicorn in the backend? Why choose FastAPI over Flask or Django?

Question 07
What is Server-Sent Events (SSE), why is it used for LLM streaming, and how does it compare to WebSockets or HTTP Polling?
Level 1 Streaming & Protocols
📌 WHAT IS THIS? (Definition & Concept)
Server-Sent Events (SSE) is an HTTP/1.1 and HTTP/2 standard that allows a client to receive automatic, asynchronous data streams from a server over a single, persistent HTTP connection.
🎯 WHY WE USE IT? (Need & Value)
Generating complete responses from a 7B LLM can take 4-10 seconds. Waiting for the complete JSON response creates perceived lag. Streaming tokens provides instant feedback (<300ms Time-to-First-Token). WebSockets are bidirectional and overkill for server-to-client LLM tokens; HTTP polling incurs huge request overhead. SSE is lightweight, works over standard HTTP, and automatically reconnects.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
FastAPI exposes StreamingResponse(event_generator(), media_type='text/event-stream'). The generator yields formatted events: event: meta (model details), event: token (individual words/characters), event: citations (bounding boxes), and event: done.
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE
Explain the protocol format: 'Each SSE message has an `event:` name and a `data:` payload, ending with double newlines `\n\n`.'
Question 08
What is Qdrant Vector Database, and why was it chosen over alternatives like Chroma or Milvus?
Level 1 Vector Database
📌 WHAT IS THIS? (Definition & Concept)
Qdrant is an open-source vector similarity search engine written in Rust, offering production-grade performance, payload-based filtering, and HNSW graph indexing.
🎯 WHY WE USE IT? (Need & Value)
Chroma relies heavily on SQLite/duckdb which can encounter concurrency bottlenecks; Milvus is complex to deploy in lightweight local setups. ⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
DocuChat initializes Qdrant on port 6333 or falls back to ./data/qdrant_storage. The doc_chunks collection stores 384-dimensional vectors with Cosine distance. Metadata payloads store chunk IDs, document names, page numbers, text, and raw bounding box lists.
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE

Question 09

Level 1 Embeddings
📌 WHAT IS THIS? (Definition & Concept)

Question 10
What is BM25 / BM25Plus, and why is vector search alone not enough for production document search?
Level 1 Lexical Search
📌 WHAT IS THIS? (Definition & Concept)
BM25 (Best Matching 25) is an industry-standard probabilistic information retrieval ranking function based on Term Frequency (TF) and Inverse Document Frequency (IDF). BM25Plus adds a positive lower bound to prevent over-penalizing long documents.
🎯 WHY WE USE IT? (Need & Value)
Dense vector search represents semantic meaning but struggles with exact lexical matching: specific product IDs, part numbers, person names, percentages, acronyms, or phone numbers. If an employee asks for 'Form W-2' or 'Candidate Roll No 4821', dense embeddings often retrieve generic tax forms or school certificates. BM25 guarantees exact keyword hits.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
During ingestion, chunk texts are tokenized (lowercased, punctuation-stripped) and indexed into a BM25Plus inverted index serialized to disk at backend/data/bm25/<doc_id>.json.
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE
Explain the complementary nature: 'Dense search solves vocabulary mismatch (synonyms); BM25 solves exact term precision. Combining them is called Hybrid Search.'
Question 11
What is a Bounding Box (BBox) in PDF processing, and how is it used in DocuChat AI?
Level 1 Document Geometry
📌 WHAT IS THIS? (Definition & Concept)
A Bounding Box is a set of geometric coordinates (x0, y0, x1, y1) defining the rectangular boundary of a text element, word, table, or paragraph on a specific document page, along with the page's natural width and height.
🎯 WHY WE USE IT? (Need & Value)
Most document chatbots only return text chunks. The user still has to read through the page to find where the statement is located. Bounding boxes enable visual provenance: the UI directly highlights the exact physical sentence on the PDF canvas.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
PyMuPDF and Docling extract word- and block-level rects during parsing. When a chunk is created, all associated bounding boxes are packaged into its metadata. After the LLM answers, the scoring engine identifies the single best box matching the answer and renders a pulsing rectangle over the PDF.
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE
Mention coordinate systems: 'PDFs traditionally use bottom-left origins, while HTML canvas uses top-left origins. Our parser normalizes coordinates to avoid inverted highlights.'

Question 13
How does the Ingestion Subsystem work from raw file upload to indexed storage?
Level 2 Ingestion Pipeline
📌 WHAT IS THIS? (Definition & Concept)
The Ingestion Subsystem processes incoming documents (PDF, DOCX, TXT, Excel) asynchronously, extracting layout structure, text elements, tables, and bounding boxes, followed by chunking and dual-database indexing.
🎯 WHY WE USE IT? (Need & Value)
Raw document files cannot be queried directly by an LLM. Ingestion must convert unstructured layout data into clean, structured chunks while preserving exact geometric coordinates for later visual verification.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
When a file is uploaded to /api/documents/upload: (1) The file is written to backend/data/uploads/<uuid>_filename; (2) An entry is added to SQLite (rag_app.db) with status 'processing'; (3) DoclingParser attempts to call the IBM Docling container on port 5001. If unavailable, it falls back to local pymupdf (Fitz); (4) Each element is parsed into a ParsedElement containing text, page number, bounding boxes, heading path, and element type; (5) StructureAwareChunker bundles elements into ~400-token chunks; (6) FastEmbed computes 384-d vectors inserted into Qdrant; (7) BM25Plus creates the lexical index on disk; (8) SQLite status updates to 'ready'.
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE
Mention the resilient fallback: 'We designed an automatic fallback from containerized IBM Docling to local PyMuPDF, guaranteeing zero ingestion failure if the Docker service is down.'
Question 14
What is Structure-Aware Chunking, why ~400 tokens with 50 overlap, and how does it handle headers and tables?
Level 2 Chunking Strategy
📌 WHAT IS THIS? (Definition & Concept)
Structure-Aware Chunking is an intelligent segmentation strategy in chunking/structure_chunker.py that respects document boundaries (headings, paragraphs, table rows) rather than arbitrarily splitting text mid-sentence.
🎯 WHY WE USE IT? (Need & Value)
Fixed-character chunking (e.g. 500 characters) cuts across tables, splits equations, and detaches headers from their body paragraphs, causing retrieval failure. Structure-aware chunking maintains full semantic context.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
The chunker accumulates ParsedElement objects. It tracks current token counts using tiktoken or whitespace approximations. When adding an element exceeds ~400 tokens, it flushes the chunk, retaining the last 50 tokens (or preceding header element) as overlap. For tables, it converts rows into markdown tables to preserve column-row relationships. Section heading paths (e.g. ['Financials', '2024 Revenue']) are prepended to every chunk.
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE
Explain the 400-token sweet spot: '400 tokens is long enough to encapsulate a complete business thought or table snippet, yet concise enough to avoid embedding dilution in 384-d vector spaces.'
Question 15
How are Bounding Boxes extracted, normalized, and mapped to specific chunks during ingestion?
Level 2 Document Geometry
📌 WHAT IS THIS? (Definition & Concept)
Bounding box extraction captures physical rectangular coordinates (x0, y0, x1, y1) for every sentence and word, normalizing them against page width and height.
🎯 WHY WE USE IT? (Need & Value)
Different PDF tools output coordinates in varying units (points, pixels, 72 DPI, 150 DPI) and differing coordinate origins (PDF standard is Bottom-Left, while web browsers use Top-Left). Normalization ensures consistent cross-platform visual rendering.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
In parsers/docling_parser.py, PyMuPDF's page.get_text('words') and page.get_text('blocks') extract rect objects alongside page dimensions (page.rect.width, page.rect.height). Each box is stored with coord_origin: 'TOPLEFT'. Crucially, the parser binds the exact word/sentence text to the box dictionary. When chunks are grouped, all constituent bounding boxes are aggregated into chunk.bboxes.
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE
Highlight text binding: 'Attaching the exact text string directly to the bounding box dict is what later enables our Global Best-Box scoring algorithm to match LLM answer tokens to exact coordinates.'

Question 17
How does Hybrid Parallel Search execute across Qdrant and BM25Plus?
Level 2 Hybrid Retrieval
📌 WHAT IS THIS? (Definition & Concept)
Hybrid Parallel Search runs dense vector similarity search and sparse lexical keyword search at the same time in parallel, merging their candidate pools.
🎯 WHY WE USE IT? (Need & Value)
Running dense search followed sequentially by sparse search doubles retrieval latency. Parallel execution minimizes response time while capturing both semantic concepts and exact keyword matches.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
In retrieval/pipeline.py, the system uses asyncio.gather:
dense_task = vector_store.search(query_vector=qvec, doc_ids=doc_ids, limit=30)
sparse_task = bm25_index.search(query=q, doc_ids=doc_ids, limit=30)
v_hits, b_hits = await asyncio.gather(dense_task, sparse_task)
FastEmbed converts the query into a 384-d vector for Qdrant, while BM25 tokenizes the text to query the JSON inverted index.
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE
Interview punchline: 'We cut retrieval latency from 90ms to 45ms by leveraging Python's asyncio event loop to query Qdrant and BM25Plus concurrently.'
Question 18
What is Reciprocal Rank Fusion (RRF), what is its mathematical formula (k=60), and why use it?
Level 2 Ranking & Fusion
📌 WHAT IS THIS? (Definition & Concept)
Reciprocal Rank Fusion (RRF) is an unsupervised ranking fusion algorithm that combines the ranked results of multiple information retrieval systems without requiring raw score normalization.
🎯 WHY WE USE IT? (Need & Value)
Cosine similarity scores from dense vectors (e.g. 0.82) and BM25 scores (e.g. 14.5) operate on completely different scales and distributions. Standard weighted addition fails because BM25 scores are unbounded. RRF relies solely on ranks, eliminating scale mismatch.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
The RRF score for a document $d$ across query methods $M$ is defined as:
$$RRF(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$
Where $r_m(d)$ is the 1-based rank of document $d$ in system $m$, and $k$ is a smoothing constant set to $60$. The constant $60$ prevents top-ranked items from drowning out items that appear consistently in ranks 2-5 across all systems.
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE
Quote Cormack et al. (2009): 'RRF with k=60 consistently outperforms individual retrieval models and tuned linear combinations without risk of overfitting.'
Question 19
What is Max-Scaled Reranking, why did you replace standard Min-Max normalization, and what bug did it fix?
Level 2 Reranking Optimization
📌 WHAT IS THIS? (Definition & Concept)
Max-Scaled Reranking is a custom score normalization technique in retrieval/reranker.py that scales raw relevance scores by the maximum score: $\text{norm\_score} = \frac{\text{raw\_score}}{\max(\text{raw\_scores})}$.
🎯 WHY WE USE IT? (Need & Value)
Industry standard Min-Max normalization: $\frac{s - \min}{\max - \min}$ has a fatal mathematical flaw in small candidate sets (e.g. 2 chunks): the lowest score chunk is always mathematically forced to 0.0! If Chunk 1 has score 0.95 and Chunk 2 has score 0.92, Min-Max makes Chunk 2 equal 0.0, causing the system to discard highly relevant secondary context if a threshold of 0.25 is applied.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
DocuChat AI replaced Min-Max with Max-Scaling. In our example, Chunk 1 gets $0.95/0.95 = 1.0$, and Chunk 2 gets $0.92/0.95 = 0.968$. Both comfortably exceed the 0.25 threshold and are retained for LLM synthesis.

Question 29
How do you check and evaluate that the RAG pipeline gives correct answers?
Level 3 RAG Evaluation & Quality
📌 WHAT IS THIS? (Definition & Concept)
RAG Evaluation is the systematic measurement of both Retrieval Quality (did we retrieve the right chunks?) and Generation Quality (is the LLM answer factual, complete, and faithful to the context?). In DocuChat AI, this is implemented in backend/eval/retrieval_eval.py with a golden test suite in backend/eval/golden_dataset.json.
🎯 WHY WE USE IT? (Need & Value)
Without rigorous quantitative evaluation, RAG pipelines silently degrade: chunking changes can break semantic recall, embedding shifts can drop key terms, and prompt adjustments can induce subtle hallucinations. Evaluating both stages independently pinpoints the exact point of failure.
⚙️ HOW IT WORKS IN DOCUCHAT AI? (Implementation & Mechanics)
DocuChat AI employs a multi-tiered evaluation methodology:
1. Retrieval Evaluation (Independent of LLM):
• Hit Rate@K (Recall@K): Measures the percentage of test queries where at least one ground-truth chunk appears in the top $K$ retrieved results ($K \in [1, 3, 5, 10]$).
• Mean Reciprocal Rank (MRR@K): Evaluates how high the first correct chunk was ranked: $MRR = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{rank}_i}$. Penalizes systems that return relevant context lower in the list.
• NDCG@K (Normalized Discounted Cumulative Gain): Accounts for both relevance and position discounting: $DCG@K = \sum_{i=1}^K \frac{\text{rel}_i}{\log_2(i + 1)}$, normalized by Ideal DCG ($IDCG$).
• Keyword Evidence Coverage: Verifies that essential keywords, entity names, and metrics from the golden set appear in the retrieved text: $\frac{\sum \mathbb{I}(\text{kw} \in \text{context})}{|\text{keywords}|}$.
• Retrieval Latency (ms): Tracks end-to-end parallel search latency.
2. Generation Quality Evaluation (RAG Triad / Ragas):
• Faithfulness / Groundedness: Are all claims in the generated response mathematically supported by the retrieved context? (Checks for hallucinations).
• Answer Relevance: Does the answer directly address the user's question without drifting?
• Context Recall: Did the retrieved context contain all facts necessary to construct the reference answer?
3. Deterministic Geometric Grounding:
• DocuChat AI has a unique verification layer: our refine_citations_for_answer() algorithm matches generated answer tokens against extracted bounding box text. If the LLM produces a fact not found in any bounding box, confidence drops and citation alignment fails.
💡 KEY INTERVIEW PRO-TIP & PUNCHLINE
This is a signature interview question. Structure your response into: (1) Component-level retrieval metrics (Hit Rate, MRR, NDCG), (2) End-to-end generation metrics (Faithfulness, Relevance), and (3) Our Golden Dataset benchmark runner in eval/retrieval_eval.py.
